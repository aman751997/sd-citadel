## When this pattern fires

You're asked about **sums (or products/counts) over ranges or subarrays**, more than once: "sum of elements between i and j, many queries", "how many subarrays sum to K", "index where left sum equals right sum". Brute force re-adds the same elements over and over — the repeated work IS the signal.

**The idea:** precompute `prefix[i]` = sum of everything before index i. Then any range is one subtraction:

```
sum(i..j) = prefix[j+1] - prefix[i]
```

**Convention that saves you off-by-ones:** make `prefix` length n+1 with `prefix[0] = 0`. Every range query works uniformly — no special case for ranges starting at 0.

## Form 1 — Standard 1D

```java
// Range Sum Query — Immutable: build once O(n), answer each query O(1)
class NumArray {
    private final int[] prefix;
    public NumArray(int[] nums) {
        prefix = new int[nums.length + 1];
        for (int i = 0; i < nums.length; i++)
            prefix[i + 1] = prefix[i] + nums[i];
    }
    public int sumRange(int left, int right) {
        return prefix[right + 1] - prefix[left];
    }
}
```

**Find Pivot Index** — no array even needed: total sum once, then walk with a running `leftSum`; pivot when `leftSum == total - leftSum - nums[i]`.

**Product of Array Except Self** — prefix thinking without sums: answer[i] = (product of everything left of i) × (product of everything right of i). Two passes, second one runs a running suffix product right-to-left directly into the answer array → O(1) extra space. The "no division" constraint is the trigger screaming *prefix decomposition*.

## Form 2 — Prefix + HashMap (the interview favorite)

"**Count subarrays summing exactly to K**" — sliding window FAILS here (negatives break the shrink logic: growing the window doesn't monotonically grow the sum). The trick:

A subarray (i..j) sums to K ⟺ `prefix[j+1] - prefix[i] = K` ⟺ `prefix[i] = prefix[j+1] - K`.

So walk left to right maintaining the running prefix, and ask a hashmap: *"how many earlier prefixes equal (current − K)?"* Each match = one subarray ending here.

```java
// Subarray Sum Equals K
public int subarraySum(int[] nums, int k) {
    Map<Integer, Integer> seen = new HashMap<>();
    seen.put(0, 1);                    // empty prefix — subarrays starting at index 0
    int prefix = 0, count = 0;
    for (int x : nums) {
        prefix += x;
        count += seen.getOrDefault(prefix - k, 0);
        seen.merge(prefix, 1, Integer::sum);   // add AFTER counting (no self-match)
    }
    return count;
}
```

Two details interviewers watch for:

1. **`seen.put(0, 1)` seed** — without it, subarrays that start at index 0 are never counted. The most common bug in this problem, period.
2. **Count before inserting** the current prefix — else a zero-K query matches itself.

**Continuous Subarray Sum** (multiple of K): same skeleton, store `prefix % k` instead of prefix, and store **first index** per remainder (need length ≥ 2, so compare indices). Same remainder seen twice = the between-chunk sums to a multiple of k.

## Recognition table

| You see | Move |
|---------|------|
| "many range-sum queries" | build prefix array, O(1) per query |
| "count subarrays with sum exactly/K-ish" (negatives possible) | prefix + hashmap of seen prefixes |
| "sum divisible by K" | hashmap of prefix **remainders** |
| "left sum equals right sum" | running leftSum vs total |
| "product except self, no division" | prefix × suffix products |
| "longest subarray with equal 0s and 1s" | map 0→−1, then prefix+hashmap (first-index variant) |

**Boundary with sliding window:** all-positive + "shortest/longest run meeting threshold" → window. Negatives present, or "count exact" → prefix+hashmap. Say which and why — that one sentence is a recognition rep.

## Bug bestiary (pre-loaded — earn your own)

- **Missing `put(0,1)` seed** → subarrays starting at index 0 silently dropped.
- **Insert before count** → K=0 self-matches inflate the answer.
- **Length-n prefix array** (no leading 0) → special-casing ranges from index 0, off-by-ones everywhere. Always n+1.
- **Int overflow** on long arrays of big values — prefix in `long`.
