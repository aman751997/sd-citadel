## When this pattern fires

The brute force compares **pairs** or rebuilds an array — O(n²) or O(n) extra space — and one of these is true: the array is **sorted** (or has exploitable structure), you're asked for a **pair/triplet** with a property, or the change is **in-place** partitioning/compaction. Two pointers replaces "compare everything with everything" with "each pointer moves at most n steps" → **O(n), O(1) space**.

Three distinct forms. Interviewers don't say which — the trigger tells you.

---

## Form I — Opposite Ends (converging)

Pointers start at both ends, move toward each other, meet in the middle. **Fires when:** sorted array + target pair, symmetry check, or maximizing something between two boundaries.

```java
// Two Sum II — sorted array, find pair summing to target
public int[] twoSum(int[] nums, int target) {
    int lo = 0, hi = nums.length - 1;
    while (lo < hi) {
        int sum = nums[lo] + nums[hi];
        if (sum == target) return new int[]{lo + 1, hi + 1}; // 1-indexed!
        if (sum < target) lo++;   // need more → only lo++ can help
        else hi--;                // need less → only hi-- can help
    }
    return new int[]{-1, -1};
}
```

**Why moving is safe (the invariant you narrate):** the array is sorted, so if `sum < target`, then `nums[lo]` paired with ANY element ≤ `nums[hi]` is also too small — `lo`'s current value is fully eliminated, not just this pair. Every step permanently discards one element. That's the proof of O(n), and saying it is what separates "memorized" from "understands".

**Container With Most Water** (you coded this) is the same skeleton with a greedy twist: move the **shorter** line, because the shorter side caps the area — keeping it while shrinking width can only lose. Same elimination logic, different justification. **Trapping Rain Water** (your queued Hard) extends it again: track `maxLeft`/`maxRight`; the side with the smaller max is fully determined → process it.

## Form II — Same Direction (Reader & Scribe)

Both pointers move left→right: the **reader** scans every element; the **scribe** marks where the next "kept" element lands. **Fires when:** in-place compaction — remove/keep/move elements without extra space.

```java
// Move Zeroes — push non-zeros left, zeros right, order preserved
public void moveZeroes(int[] nums) {
    int scribe = 0;                          // next slot for a non-zero
    for (int reader = 0; reader < nums.length; reader++) {
        if (nums[reader] != 0) {
            if (reader != scribe) {          // minimize-writes guard (your variant)
                int t = nums[scribe]; nums[scribe] = nums[reader]; nums[reader] = t;
            }
            scribe++;                        // scribe steps EVEN when reader==scribe
        }
    }
}
```

**The invariant (say it before coding — your logged habit-gap):** *everything left of `scribe` is final and correct; everything between `scribe` and `reader` is discard/unprocessed territory.* Every reader step maintains it. When the reader finishes, `[0, scribe)` is the answer.

**Remove Duplicates II** (your first unseen win) shows the form's flexibility: "keep at most 2" → the keep-condition becomes `nums[reader] != nums[scribe-2]`. The skeleton never changes; only the keep-condition does. **Dutch National Flag** (Sort Colors) upgrades to **three** pointers: `low` (next 0 slot), `mid` (reader), `high` (next 2 slot) — and the one rule that broke you once and never again: **after swapping with `high`, `mid` stays** (the swapped-in element is unexamined); after swapping with `low`, `mid` advances (it received a known 1... or was `mid==low`'s own element).

## Form III — Two Iterables

One pointer per sequence, advancing by comparison rule. **Fires when:** merging sorted things, subsequence checks.

```java
// Merge Sorted Array — nums1 has buffer space at its END → merge BACKWARDS
public void merge(int[] nums1, int m, int[] nums2, int n) {
    int i = m - 1, j = n - 1, w = m + n - 1;   // w = write position, from the back
    while (j >= 0) {                            // nums2 leftovers are the only real work
        if (i >= 0 && nums1[i] > nums2[j]) nums1[w--] = nums1[i--];
        else                               nums1[w--] = nums2[j--];
    }
    // i-leftovers are already in place — that's WHY we merge backwards
}
```

**The insight to narrate:** merging forward overwrites unread `nums1` elements; the free space is at the end, so write from the end, largest-first. Loop condition `j >= 0` (not `i`) — if `nums2` is exhausted, remaining `nums1` prefix is already correctly placed. You quizzed 3/3 on exactly this — keep it warm.

Subsequence check (Append Characters): reader walks the big string, pointer on the pattern advances only on match; leftover pattern = answer.

## Bug bestiary (yours, earned)

- **Stale read after overwrite** (Valid Palindrome O(1) rewrite) — read a value you already overwrote. Guard: in-place = think swap, not copy.
- **Exit-condition narration slip** (Sort Colors: said `2<=2`, was `2<=1`) — trace the LAST iteration by hand before declaring done.
- **`mid` advances after high-swap** — it must not; the swapped-in element is unexamined.
- **Scribe forgets to step when `reader==scribe`** in minimize-writes variant — scribe counts kept slots, not swaps.
