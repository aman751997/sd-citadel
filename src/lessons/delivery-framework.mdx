## Why a framework at all

A system design interview is not a knowledge test — it's a **structured conversation you are expected to drive**. The single biggest differentiator between a hire and a no-hire at the same knowledge level is whether the candidate controls the clock or the interviewer does.

The framework below is the industry-standard spine (the same one Hello Interview teaches). You will run it on **every** problem, from URL shortener to Uber. The phases never change. Only the content does.

## The six phases

| # | Phase | Budget | Output |
|---|-------|--------|--------|
| 1 | Requirements | 0–5 min | Agreed scope: 2–3 functional flows + the non-functionals that shape the design |
| 2 | Estimation | 5–10 min | Numbers that **change decisions** — QPS, storage, working set |
| 3 | API + Data Model | 10–15 min | Core endpoints + entities, M:N joins named explicitly |
| 4 | High-Level Design | 15–30 min | Boxes and arrows; one core flow traced end-to-end |
| 5 | Deep Dives | 30–42 min | 2–3 hard parts, each ending in a committed decision |
| 6 | Wrap-Up | 42–45 min | Bottlenecks, monitoring, what breaks at 10× |

## Phase 1 — Requirements (the phase you already do well)

Two lists, spoken out loud:

**Functional** — "Users can shorten a URL. Users can hit a short URL and get redirected. Out of scope: analytics dashboard, custom aliases." The *out of scope* sentence is not optional — it's how you buy time for depth later, and interviewers score it as maturity.

**Non-functional** — only the ones that will actually shape your design:

- **Scale**: DAU, read/write ratio. This decides caching and sharding.
- **Latency**: is there a number? ("redirect must feel instant" → p99 < 100ms)
- **Consistency vs availability**: which does this system prefer when partitioned?
- **Durability**: can we ever lose a record?

> **The bridge sentence** (memorize the shape): *"So to summarize: we're building X and Y at Z scale, prioritizing availability over consistency — does that match what you had in mind?"* — then wait for the nod. That nod is your contract.

## Phase 2 — Estimation (covered in depth next lesson)

One rule here: **only compute numbers that change a decision.** "1M QPS" matters because it forces a cache tier and horizontal scaling. "37 GB of logs" matters because it fits one Postgres box. A number that doesn't end in a design conclusion was wasted breath.

## Phase 3 — API + Data Model

Endpoints: method + path + body, core flows only.

```
POST /urls          { longUrl }            → { shortCode }
GET  /{shortCode}                          → 302 Location: longUrl
```

Entities: name them, then name the **relationships** — and say the cardinality out loud. (Known trap from your own mock history: Role↔Permission modeled as 1:N when it's M:N. The fix is a habit: every pair of entities, ask "can each side have many of the other?" If yes twice → join table, say its name.)

## Phase 4 — High-Level Design

Draw client → gateway/LB → service(s) → store(s). Then **trace one core flow through every box you drew**, out loud: "The POST hits the gateway, gateway routes to the URL service, service generates a code, writes to Postgres, returns."

Rule: every box earns its existence in one sentence. A box you can't justify is a box the interviewer will delete in front of you.

## Phase 5 — Deep Dives (where offers are won)

Pick 2–3 hard parts — or take the interviewer's hint if they poke at one. Per dive, run this shape:

1. **Name the problem** — "code generation collisions under concurrent writes"
2. **Two options** — counter service vs random + retry
3. **Tradeoff in one line each**
4. **Commit** — "I'll take random base62 with retry-on-conflict; at our write QPS collisions are rare and it removes the counter as a single point of failure."

> The hand-wave rule: **a cache is not a design decision until it has a key shape, a TTL with a reason, and an invalidation story.** "We'll cache in Redis" scores zero. "Cache `code → longUrl`, TTL 24h since mappings are immutable, no invalidation needed" scores.

## Phase 6 — Wrap-Up

Thirty seconds: "The bottleneck at 10× is X, I'd shard by Y, and I'd want dashboards on Z before launch." Ending strong is disproportionately memorable.

## The meta-skill: narrating transitions

Interviewers can't read your mind mid-silence. The framework gives you stock transition sentences — use them verbatim until they're reflex:

- "Before I design, let me get a feel for the numbers." (→ estimation)
- "The numbers say [conclusion], so here's the shape I'd start with." (→ high-level)
- "The hard part here is clearly [X] — let me go deep on it." (→ deep dive)
- "With the time left, let me flag what I'd do next." (→ wrap-up)

## Drill for this week

Run phases 1–3 only (no design) on three problems as a speed drill — 15 minutes each: **Pastebin, Instagram, a parking lot app**. The goal is the transitions becoming automatic, not the designs being good.
