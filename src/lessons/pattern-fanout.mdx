## The pattern in one sentence

One user's action must appear to many users (followers, subscribers, channel members) — and you must choose **when** the expensive many-copies work happens: at write time (push), at read time (pull), or split by who's writing (hybrid).

**Trigger words:** "feed", "timeline", "followers see", "subscribers", "notify all members", "home page shows posts from people you follow".

## The two pure strategies

**Pull (fan-out on read):** store each post once, by author. Building Alice's feed = fetch recent posts from all 800 people she follows, merge, rank, return.

**Push (fan-out on write):** every user has a materialized **feed cache** (Redis list/sorted set of post IDs). When Bob posts, a fan-out worker inserts the post ID into every follower's feed. Reading a feed = one cache read.

| | Push | Pull |
|--|------|------|
| Read cost | O(1) — the product wants this; feeds are read 100:1 | O(followees) per read — expensive, slow |
| Write cost | O(followers) per post | O(1) |
| Killer case | **celebrity posts** → 100M feed inserts for one tweet | **heavy reader** following thousands |
| Staleness | feed materializes seconds after post (async workers) | always fresh |

## The celebrity problem and the hybrid answer

Push dies at celebrities: one Ronaldo post = 600M writes, and the fan-out storm delays everyone else's posts behind it. Pull dies at read volume. So every real system converges on **hybrid**:

- **Normal users (99.9%): push.** Their follower counts are small; write fan-out is cheap; reads stay O(1).
- **Celebrities (past a threshold, say 100K followers): pull.** Their posts are stored once. At read time: fetch feed cache (pushed part) + fetch recent posts from the few celebrities you follow (pulled part) + **merge and rank**.

Alice follows 799 normies + Ronaldo → her read = 1 cache read + 1 celebrity lookup + merge. This exact paragraph, with a threshold number said out loud, is the expected answer to the most-asked scale question in SD interviews (Twitter/Instagram feed).

Implementation notes that earn depth: fan-out runs **async via queues** (post write returns instantly; feed inserts are the queues lesson's exact diagram — key by follower ID for parallelism); feed caches hold **IDs only, not content** (hydrate post content from a post cache at read — dedups storage, edits propagate free); cap feed length (~800 entries — beyond page 3 nobody scrolls; fall back to pull for archaeology); a new user with an empty feed cache gets a one-time pull build.

## Questions this pattern unlocks

| Bank question | How the pattern applies |
|---------------|------------------------|
| **Twitter / News feed** (walkthrough next) | the pattern verbatim — hybrid + ranking |
| **Instagram** | same + media via blob/CDN lesson; feed = IDs, images = CDN |
| **Notification system** | fan-out to devices instead of feeds; add per-channel workers (push/email/SMS), priorities, retry+DLQ |
| **TikTok / recommendations feed** | pull, but candidates come from a ranker, not a follow graph — meets AI-era recsys lesson |
| **Discord huge channels** | push to online members only (registry from realtime lesson), lazy for offline |
| **Live comments** | fan-out to current viewers of a stream = pub/sub push, no persistence per viewer |
