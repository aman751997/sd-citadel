## The pattern in one sentence

Multiple devices hold **copies** of shared state, edit them independently (offline, concurrently), and the system must reconcile divergent copies — the answer escalates from "detect and punt" to "merge automatically," and knowing *which rung the product needs* is the whole game.

**Trigger words:** "sync across devices", "offline edits", "collaborative", "both users edited", "conflict".

## Rung 1 — Detect and punt (Dropbox files)

For opaque files, don't be clever. Use **version vectors** (or a simple per-file version counter): client says "I'm editing version 7"; if the server is already on 8, that's a **conflict** — and Dropbox's famously right answer is to *punt*: keep both, name one `file (conflicted copy)`, let the human decide. Merging binary files automatically destroys data. **Saying "I will not auto-merge here" is a senior answer**, not a cop-out.

The sync machinery around it (blob lesson does the details): chunk + hash files, upload changed chunks, notify other devices (realtime lesson — long-poll/WS), they pull the delta.

## Rung 2 — Last-writer-wins and its lie

LWW = timestamp each write, latest wins. Cheap, built into Dynamo-style stores, and **silently loses data** — the "loser" write vanishes without anyone deciding that. Acceptable for: presence, cursor position, a settings toggle — data where the newest value genuinely supersedes. Unacceptable for: documents, carts, counters. Also: distributed clocks skew, so "last" is partly fiction. Use the phrase "LWW is acceptable here *because losing the older write is the correct product behavior*" — or don't use LWW.

## Rung 3 — OT: transform concurrent edits (Google Docs classic)

Live text editing can't punt (conflicts every second) and can't LWW (loses keystrokes). **Operational Transformation**: represent edits as operations (`insert("x", pos 5)`), and when two ops race, **transform** one against the other so both converge:

The architecture consequence interviewers probe: OT needs a **central server per document** to sequence operations. That's fine (a doc has few concurrent editors — this is NOT a horizontal-scale problem; it's a per-doc-session one) and it gives you the op log for free = **version history**. Shard doc-sessions across servers by `doc_id` (consistent hashing — patterns compose), cursors/presence broadcast over the doc's WS room (realtime lesson).

## Rung 4 — CRDTs: merge without a sequencer

**Conflict-free Replicated Data Types**: data structures whose merge is mathematically commutative — any replicas, merging in any order, converge without coordination. Examples: a grow-only counter (per-node counts, merge = element-wise max), an add/remove set with tombstones, sequence CRDTs for text (each character gets a stable unique ID between its neighbors — position-shifting, OT's hard part, disappears).

| | OT | CRDT |
|--|----|------|
| Coordination | central sequencer per doc | none — peer-to-peer, offline-first |
| Complexity | transform functions (fiddly, well-trodden) | metadata overhead (IDs/tombstones grow) |
| Used by | Google Docs | Figma-style apps, Riak, collaborative offline-first apps |

Interview verdict to give: "Docs-style with a server anyway → OT is proven and the server doubles as history. Offline-first or peer-to-peer → CRDTs. I'd start OT." Naming both + choosing beats deep internals of either.

## Questions this pattern unlocks

| Bank question | How the pattern applies |
|---------------|------------------------|
| **Dropbox** (walkthrough) | rung 1: version vectors + conflicted copies + chunk delta sync |
| **Google Docs** (walkthrough) | rung 3: OT + sequencer + WS rooms + op-log history |
| **Google Calendar** | mostly rung 1/2 per-field: events are structured rows — field-level LWW + invite-state machine |
| **Figma-like canvas** | CRDT per object property (LWW-per-property is honest here — newest position wins) |
| **Collaborative cart / notes** | small CRDTs (add-wins set) or server-serialized ops — say scale doesn't demand cleverness |
| **Offline-first mobile apps** | queue local ops, replay on reconnect, resolve by rung 1–4 per data type |

## Drill hand-off

With the buddy: the escalation drill — 6 data types (file, doc text, cursor, cart, calendar event, canvas object), you assign each a rung + one-line justification, 60 seconds each. Weekend mock: **Dropbox** (rung 1 + blob lesson) or **Google Docs** (rung 3) — the pattern's two walkthroughs.
