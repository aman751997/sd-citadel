## The pattern in one sentence

Millions of tiny timestamped events pour in; nobody ever reads them individually — they read **summaries over windows** (p99 last 5 min, top-10 today, views this hour). The design job: absorb the firehose cheaply and precompute the summaries readers actually ask for.

**Trigger words:** "metrics", "analytics", "dashboard", "leaderboard", "trending", "view counts", "alerts on thresholds", "clicks per campaign".

## Tool 1 — Pre-aggregation: never store what you won't read

The naive design stores every raw event and computes `AVG(...)` at query time — dead at scale (a dashboard query scanning 100M rows per refresh). Instead, **aggregate on ingest**:

<Mermaid code={`flowchart LR
    E["events firehose\n(1M/s)"] --> K[("Kafka\nkeyed by series")]
    K --> AGG["stream aggregators:\nper minute, per series:\ncount, sum, min, max, p99"]
    AGG --> TS[(time-series store\n1-min rollups)]
    TS --> RU["background rollups:\n1min → 1hr → 1day"]
    D["dashboards"] -->|"read tiny\nprecomputed rows"| TS`} />

- **Resolution ladder + retention:** raw/1-min data kept days, 1-hour kept months, 1-day kept years. Storage estimate collapses (estimation lesson: say the ladder), and old-data queries stay fast because they read coarse rollups.
- **Percentiles don't average** — you can't combine two p99s. Store **histograms/sketches** per window and merge those. One sentence, big signal.
- Late events (mobile clients, retries) → **watermarks**: "window closes at T+2min; later events go to a correction path." Name it, don't derive it.

This is "move work to write time" again — the same trade as feed fan-out and typeahead top-K. Third appearance; by now you should *see* it coming on unseen problems.

## Tool 2 — Sharded counters: when one number is too hot

A viral video's view counter takes 100K increments/sec — a single row/key melts (hot key, fourth costume). Fix: **split the counter into N shards** (`views:{video}:{0..15}`), increment a random shard, read = sum of 16. Write contention drops 16×; reads pay a small fan-in. Batch further in the app (accumulate 100 locally, flush one +100) when "views" tolerates seconds of lag — which it always does.

## Tool 3 — Top-K and the honest approximation

"Top 10 trending" over a firehose has an exact answer only if you count *everything* — often impossible in memory (millions of distinct keys). Two-level standard answer:

- **Exact, bounded keyspace:** Redis **sorted set** (`ZINCRBY views:1h video123`) → `ZREVRANGE 0 9` is the leaderboard. Works to millions of members; say the memory estimate.
- **Approximate, unbounded keyspace:** **count-min sketch** — a fixed-size 2D array of counters updated via k hashes; overestimates slightly, never underestimates; pair with a small heap of current top-K candidates. The sentence to say: *"exact counting of every URL/search-term doesn't fit memory; a count-min sketch gives top-K with bounded error in kilobytes."* Interviewers accept the name + property; they rarely want internals derived.

Windowing for "trending last hour": maintain per-minute sorted sets and union/decay them, or bucket-per-window sketches — say buckets, avoid inventing sliding-window magic on the spot.

## Storage: why time-series stores are LSM-shaped

Write-heavy append workloads fit **LSM trees** (memtable → flushed immutable SSTables → compaction) — sequential writes, no in-place updates, which is why Cassandra/InfluxDB/ClickHouse-family engines win here over B-tree row stores. Plus columnar layout + delta/gorilla compression: metrics compress ~10×+ because consecutive values barely change. Two sentences total — storage-engine depth beyond this only if the interviewer digs.

The other disease to name: **cardinality explosion** — a `user_id` tag on a metric turns 1 series into 50M. Tag design (bounded-cardinality labels only) is the operational fix; it's the Datadog walkthrough's favorite deep dive.

## Questions this pattern unlocks

| Bank question | How the pattern applies |
|---------------|------------------------|
| **Metrics / Datadog** (walkthrough) | the whole pattern + cardinality + alerting (sliding threshold checks on rollups) |
| **Ad click aggregator** | stream aggregation + exactly-once-ish counting (contention lesson) + watermark windows |
| **Top-K / leaderboard** | sorted sets vs count-min, windowing |
| **YouTube view counts** | sharded counters + periodic flush to truth |
| **Trending topics** | count-min + per-window buckets + decay |
| **Distributed tracing ingest** | span firehose + sampling + time-partitioned storage |
| **Strava heatmaps** | geo (previous pattern) + time bucketing — patterns compose |
