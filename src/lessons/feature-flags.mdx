## Why this is a real interview question

Atlassian, LaunchDarkly, and increasingly everyone asks it — because it looks small ("if-statement as a service") and is actually a distributed config + statistics problem. It's also the rare design where **read latency ~0 is a hard requirement**: flag checks sit in every request's hot path, thousands of times per second.

## The core decision: evaluate locally, distribute config

A flag check must never be a network call. So the architecture inverts the naive design:

<Mermaid code={`flowchart LR
    A["admin UI"] --> CS["config service\n+ Postgres (truth,\nversioned, audited)"]
    CS -->|"SSE / streaming push\n(realtime lesson)"| SDK1["app server SDK\n(full ruleset in memory)"]
    CS -->|"..."| SDK2["app server SDK"]
    SDK1 -->|"evaluate locally\n~microseconds"| REQ["request path"]
    SDK1 -.->|"poll fallback +\nlast-known-good on disk"| CS`} />

- **SDKs hold the entire ruleset in memory** and evaluate locally: ~µs, zero network.
- **Changes stream to SDKs via SSE** (server push — one-way, realtime lesson's decision rule applied) with polling as fallback; propagation in seconds.
- **Bootstrap resilience:** SDK starts while config service is down → last-known-good ruleset from local disk + safe defaults compiled in. "The flag system must never take the product down" is the availability sentence.
- Truth lives in Postgres — versioned, audited ("who turned this on Friday 5pm").

**The kill switch is the product's whole pitch:** bad deploy behind a flag → toggle off → seconds-wide blast radius, no rollback deploy. Say that before the interviewer asks what flags are for.

## Sticky bucketing — deterministic, not stored

Users must get the *same* variant every time (flapping UIs break users AND experiments). Wrong answer: store user→variant rows (billions of rows, a lookup on the hot path — everything we just avoided). Right answer:

```
bucket = hash(user_id + flag_key) % 10000
→ variant by range: [0–4999] control, [5000–9999] treatment
```

Deterministic, stateless, no storage, instantly consistent everywhere. Salting by `flag_key` matters: without it, the same users land in "treatment" for *every* experiment (correlated cohorts poison all your results). Rollout 5%→50% = widen ranges; **already-bucketed users never flip** — say it.

## Enough experimentation statistics (four sentences, no more)

1. **Randomization is the point** — hash-bucketing gives unbiased cohorts; assignment must precede (and not correlate with) behavior.
2. **Fix sample size / duration up front** — peeking at p-values daily and stopping when it looks good manufactures false positives.
3. **Log exposure, not assignment** — analyze only users who actually *hit* the flagged code path; counting never-exposed users dilutes the effect.
4. **Guardrail metrics** alongside the goal metric — the experiment that lifts clicks 2% and crashes retention should die automatically.

That's the depth interviews want. If they push deeper, it's a data-science interview wearing a costume — say you'd pull in the stats platform.
