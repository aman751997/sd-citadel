## The pattern in one sentence

When data outgrows one node you split it by key across many — and the *method* of splitting decides what happens on the day you add node 11 to a 10-node cluster, which is the day naive designs die.

**Trigger words:** any "design a distributed X" (cache, KV store, object store), "how does it scale horizontally?", "what happens when you add a node?"

## Why modulo hashing fails

`node = hash(key) % N` distributes beautifully — until N changes. Going 10 → 11 nodes changes the answer for **~91% of keys**: nearly every key now lives "somewhere else." For a cache, that's a total cold start (stampede at the DB); for a store, a full data reshuffle. The interviewer's "what happens when you add a node?" is aimed exactly here.

## Consistent hashing — the fix

Hash node IDs and keys onto the same circular space (the **ring**). A key belongs to the **first node clockwise** from it:

Add node D at 0.5: only keys in (0.4, 0.5] move — from C to D. **Adding/removing a node moves ~1/N of keys, not ~all.** That single sentence is the pattern's payoff — say it verbatim.

**Virtual nodes (the mandatory follow-up):** few physical nodes = lumpy, unfair arc sizes; and a removed node dumps its whole arc onto one neighbor. Fix: each physical node appears at ~100–1000 points on the ring ("vnodes"). Load evens out statistically; a dead node's arcs scatter across *everyone*; and **heterogeneous hardware** gets handled by giving bigger boxes more vnodes. Consistent hashing without vnodes is half an answer — interviewers know it.

Who uses it: Dynamo/Cassandra (data placement), Redis-cluster-style caches, Kafka consumer↔partition-ish balancing, sticky routing at LBs (load-balancing lesson). One mechanism, four appearances — pattern recognition again.

## Range partitioning — the other honest option

Split by key **ranges** (users A–F → node 1) instead of hash. You lose uniform spread but gain **ordered scans**: "all events for March" hits one partition instead of all of them. This is HBase/Bigtable's choice, and why time-series systems lean range.

| | Hash | Range |
|--|------|-------|
| Load spread | uniform (hash randomizes) | can hotspot (today's writes all land in the newest range) |
| Range scans | scatter-gather every node | one/few partitions ✅ |
| Pick when | point lookups dominate (caches, KV) | time/ordered scans dominate (metrics, logs) |

The hybrid worth knowing: **compound keys** — hash on a partition key, range-sort within it (`(user_id) → time`). "All of user 42's messages this week" = one partition, one ordered scan. This is literally Cassandra's data model and DynamoDB's PK/SK — one sentence connects three technologies.

## Hot partitions — the recurring disease

Every partitioning scheme has the same failure: one key/range takes disproportionate traffic (celebrity user, today's date, viral post). The toolkit, in escalation order:

1. **Better key** — compose it: `date` → `date#hash(user)%16` splits today's writes 16 ways (at the cost of 16 reads to reassemble — say the cost).
2. **L1 cache** for hot *reads* (caching lesson's celebrity fix).
3. **Split the hot partition** — good stores auto-split by load (Bigtable), or you add vnode weight.

Note the rhyme: hot partition ≡ hot shard (databases) ≡ hot key (caches) ≡ hot Kafka partition. **One disease, four costumes** — diagnosing it fast on unseen problems is exactly the transfer skill this campaign trains.

## Rebalancing operationally (one breath)

Data doesn't teleport when the ring changes: the new owner **streams data from the old owner** while traffic continues (serve reads from old until cutover), throttled so the transfer doesn't eat production IO. Meanwhile replication (core-concepts lesson: each arc lives on the next R nodes clockwise → quorum reads/writes) keeps a node death survivable. That connects this lesson to Dynamo's whole design — the KV-store walkthrough composes exactly these pieces.
