## The anatomy of one request

Every design you'll ever draw starts with "client sends a request." Here's what actually happens, because interviewers probe it:

<Mermaid code={`sequenceDiagram
    participant C as Client
    participant D as DNS

    C->>D: where is api.example.com?
    D-->>C: 34.120.x.x (cached with TTL)

**DNS** resolves name → IP. It's a hierarchical, heavily cached system — the TTL on a record is a real design lever: low TTL (60s) lets you fail over fast but increases lookup load; high TTL (24h) means a bad record haunts you for a day. GeoDNS returns different IPs by region — the cheapest form of "route users to the nearest datacenter."

**TCP** gives you reliable, ordered bytes — at the cost of a handshake round trip. **TLS** adds encryption — another round trip or two. This is why HTTPS connection setup to a far region is slow, and why we keep connections alive and pooled.

## TCP vs UDP — the one-liner each

| | TCP | UDP |
|--|-----|-----|
| Guarantees | delivery, ordering | none — fire and forget |
| Cost | handshake, head-of-line blocking | nearly free |
| Use | almost everything (HTTP, DBs) | video calls, game state, DNS — where a late packet is worse than a lost one |

Interview line: "Zoom uses UDP because a 2-second-old video frame is garbage — better to drop it than block newer frames behind it (head-of-line blocking)." That sentence covers 90% of UDP questions.

## HTTP versions — what changed and why you care

- **HTTP/1.1** — one request at a time per connection. Browsers open ~6 parallel connections to cope.
- **HTTP/2** — multiplexes many requests over one connection, binary framing, header compression. Killed the "bundle everything into one file" era.
- **HTTP/3 (QUIC)** — runs on UDP to remove TCP's head-of-line blocking; faster handshakes, connection survives IP change (mobile).

You need one design-relevant fact: HTTP/2 multiplexing is why gRPC (built on it) handles many concurrent internal calls on few connections.

## REST vs gRPC vs GraphQL

| | Best for | Why |
|--|---------|-----|
| **REST + JSON** | public APIs, interviews' default | universal, cacheable, debuggable |
| **gRPC** | internal service-to-service | binary protobuf (small, fast), streaming, generated clients — but browsers can't speak it natively |
| **GraphQL** | client-shaped reads over many resources | one round trip for nested data; costs server complexity, caching gets harder |

Default in interviews: **REST for the public API, gRPC inside** if microservices come up. Only reach for GraphQL when the problem is literally "mobile clients need flexible nested reads" (e.g., a content app aggregating many entities per screen).

## Where TLS terminates, and the stateless rule

The load balancer usually terminates TLS (decrypts), so app servers see plain HTTP — simpler, and lets the LB route on the URL (L7 — next lessons). Everything behind it should be **stateless**: any server can handle any request, session identity comes from a signed token (JWT) or a shared session store, not server memory. Stateless servers = horizontal scaling = the assumption every design you draw depends on. If a server holds state (WebSocket connections, in-progress uploads), you must say how requests find the right server — that's a deep dive, not an accident.
