## The pattern in one sentence

Work that can't finish inside a request (too slow, too big, too flaky, or triggered by schedule) becomes a **job**: persisted, queued, executed by scalable workers, tracked by status — and every long-running feature in every design is this one template re-skinned.

**Trigger words:** "process the video", "generate a report", "send to all", "crawl", "index", "run nightly", "it can take minutes".

## The template

Speak it in this order — each numbered piece is a sentence:

1. **Persist the job first, then enqueue the ID.** The DB row is truth; the queue is a delivery mechanism. (Queue message lost → a reconciler re-enqueues rows stuck in `queued`. Queue-only jobs vanish silently.)
2. **Return `202 + job_id` immediately.** The user experience of async is "accepted, here's your tracking number."
3. **Workers pull, do, update status.** Stateless, scaled on **queue depth** (the autoscaling metric — say it).
4. **Status flows back** — polling `GET /jobs/{id}` is fine (realtime lesson: poll when you can); SSE/WS for progress bars.
5. **Failures are the design**: retries with exponential backoff + jitter, then **DLQ + alert** (queues lesson). Worker crashes mid-job → lease/visibility timeout returns the job to the queue → someone else retries → therefore **the work must be idempotent** (contention lesson: dedupe key or naturally idempotent writes).

That last chain — *crash → redelivery → idempotency* — is the pattern's core insight and the follow-up every interviewer runs.

## Pipelines — jobs that make jobs

Real work is often staged: video upload → split → transcode each chunk × each resolution → thumbnail → manifest → publish. Chain the template: each stage consumes from its queue and produces to the next, with the job store tracking a **state machine per item** (`uploaded → transcoding → packaged → live`).

Why stages beat one mega-job: independent scaling (transcode needs 50 workers, thumbnails need 2), independent retry (a failed thumbnail doesn't redo the transcode), parallelism inside a stage (4K transcode = many chunk-jobs fanned out and joined). "Fan out chunks, join on completion counter" — a Redis atomic decrement hitting zero triggers the next stage — is the standard join answer.

## Scheduled jobs — the scheduler's two problems

"Run this at 9am daily" adds two hard sub-problems on top of the template:

- **Firing on time at scale:** don't poll the whole jobs table every second. Standard: a **due-time index** queried each tick (`WHERE next_run <= now LIMIT batch`), or a delay-queue / timing-wheel. Fine-grained answer only if pushed.
- **Firing exactly once when the scheduler is replicated:** two scheduler nodes must not both fire the 9am job. This is contention: **lease on the job** (lock + TTL + heartbeat) or partition the job space so each node owns a slice. Plus idempotent execution as the backstop — belt and suspenders, name both layers.

This is why "design a distributed job scheduler" is a Tier-4 question: it's this pattern + contention + the queues lesson composed. You already own all three pieces.

## Questions this pattern unlocks

| Bank question | How the pattern applies |
|---------------|------------------------|
| **YouTube** (walkthrough) | the canonical pipeline: upload → chunk transcode fan-out/join → CDN publish |
| **Web crawler** (walkthrough) | self-feeding pipeline — workers produce new jobs (URLs) into their own frontier queue + politeness rate limits + Bloom dedup |
| **Notification system** (walkthrough) | fan-out (feeds pattern) into per-channel pipelines with retry/DLQ per provider |
| **Job scheduler** (walkthrough) | the template + due-time firing + lease-based exactly-once |
| **LeetCode judge** | jobs into sandboxed workers (containers), per-user quotas, status via poll |
| **Report generation / data export** | the template verbatim — the most common "boring" interview add-on |
