## Your personal stakes in this lesson

From your own mock logs: *"Cache in Redis" without key shape, TTL rationale, or invalidation strategy — interviewer red flag.* This lesson exists to make that sentence impossible for you to say again.

**The rule: a cache in your design is these four things, spoken out loud, or it doesn't count:**

1. **Key shape** — exactly what string maps to exactly what value
2. **TTL + why that number**
3. **Invalidation story** — what happens when the underlying data changes
4. **Failure plan** — what happens when the cache is cold, down, or stampeded

## Where caches live

<Mermaid code={`flowchart LR
    B["Browser cache"] --> CDN["CDN edge"] --> GW["Gateway"] --> APP["App server\n(local in-process cache)"] --> R[("Redis\n(distributed cache)")] --> DB[(Database)]`} />

Each layer trades freshness for distance: browser and CDN are fastest and stalest; Redis is the workhorse shared truth-ish layer; the DB is truth. In interviews, "cache" usually means the Redis layer — but mentioning "immutable assets go to the CDN and never hit us" is free credit.

## Cache-aside — the default read pattern

```
value = redis.get(key)
if miss:
    value = db.query(...)
    redis.set(key, value, ttl)
return value
```

App code owns the logic; cache holds only what's actually read (hot set). This is the answer for ~90% of interview caching. Alternatives worth one sentence each: **write-through** (write to cache + DB together — reads always warm, writes slower), **write-behind** (write to cache, flush to DB async — fast but you can lose writes; rare, say it only with a durability caveat).

## Invalidation — the part that makes it a real design

When the DB row changes, your cache is now a liar. Three honest strategies:

| Strategy | How | When it's right |
|----------|-----|----------------|
| **TTL-only** | let entries expire; tolerate staleness ≤ TTL | data where bounded staleness is fine (profiles, product pages) |
| **Delete-on-write** | after DB write, `DEL` the key; next read repopulates | the default when writers go through your app code |
| **Event/CDC-driven** | DB change stream (Debezium etc.) drives deletes | many writers / other services touch the DB |

Two rules that show seniority:

- **Delete, don't update, the cache on writes.** Updating cache + DB as two non-atomic writes under concurrency can strand a *permanently* wrong value (two writers race, cache ends up with the loser). Delete is self-healing: worst case is one extra miss.
- **TTL is your backstop even when you invalidate** — set it anyway; it caps the damage of any missed invalidation.

The one-liner to say in every design: *"Cache-aside on key `user:{id}:profile`, TTL 15 min as staleness bound, delete-on-write for immediate consistency on the user's own edits."* Four components, one breath.

## Key design

- **Namespace, always**: `feed:user:123:page:1`, not `123`. Prevents collisions, enables targeted invalidation, makes debugging humane. Multi-tenant? Tenant goes in the key (`t:42:user:123` — you already know this instinct from your day job).
- **Version escape hatch**: prefix like `v2:feed:...` lets you invalidate an entire scheme by bumping the version — no scanning keys.
- **Value granularity**: cache whole objects (`user:123` → JSON blob) by default; per-field hashes only if fields update independently at meaningfully different rates.

## The three classic failure modes (deep-dive gold)

**1. Stampede (thundering herd).** A hot key expires; 10,000 concurrent requests all miss and all hit the DB at once. Fixes: **per-key mutex** (first miss recomputes, rest wait), **stale-while-revalidate** (serve the expired value while one worker refreshes), or **jittered TTLs** so a whole class of keys doesn't expire in the same second.

**2. Hot key.** One key (celebrity profile) takes 500K reads/sec — melts its Redis shard. Fixes: **local L1 cache** in each app server with a very short TTL (1s absorbs almost everything, staleness bounded at 1s), or replicate the key across shards (`key#1..N`, read a random copy).

**3. Cache down.** If Redis dies, does the DB survive the full read load? If not, your cache is load-bearing — say so: circuit-break, shed load, or serve degraded responses. "The cache is an optimization" is only true if you've checked the DB survives without it.

## Eviction + sizing

Memory full → something leaves: **LRU** (default, recency), LFU (frequency — better for stable hot sets), TTL-based. Interview default: "LRU, and I've sized the working set" — recall the estimation lesson's move: hot set 4 GB → one node's RAM, cluster only for availability/throughput. That sentence chain (working set → node size → cluster reason) is exactly what "no hand-waving" sounds like.
