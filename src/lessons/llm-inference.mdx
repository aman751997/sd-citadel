## Why this question exists (and why you have an edge)

"Design ChatGPT's serving layer" is the new Tier-5 favorite (Microsoft, Amazon, OpenAI, Anthropic, Google all ask it). Most candidates apply web-service intuition and die, because LLM inference violates three assumptions: requests are **seconds-to-minutes long**, the bottleneck is **GPU memory**, not CPU/IO, and output arrives **incrementally**. You integrate LLMs at work — this lesson turns that into interview vocabulary.

## The shape of one request

Two phases with different economics:

1. **Prefill** — the whole prompt processes in parallel (compute-bound, fast per token).
2. **Decode** — output generates **one token at a time**, each step needing all previous context (memory-bandwidth-bound, the long tail).

The state that makes decode possible is the **KV cache**: attention keys/values for every token so far, kept in GPU memory. Rule-of-thumb numbers to say: for a mid-size model it's **~100s of KB–MB per token**, so a 32K-token context can hold **gigabytes per request** — GPU RAM, not compute, caps concurrency. That single fact drives the whole design.

## Batching — the throughput lever

GPUs are efficient at big matrix ops; serving one request at a time wastes 90%+ of the hardware. But naive (static) batching — wait, collect 16 requests, run them together — forces short answers to wait for the batch's longest answer.

**Continuous batching** (vLLM's core idea, the expected answer): the batch is rebuilt **every decode step** — a finished request exits immediately, a queued one joins mid-flight. Throughput of batching, latency close to solo serving. Name it, explain it in one sentence, done.

Admission control follows: the scheduler admits requests based on **projected KV memory** (prompt length + max output), not request count. "Our concurrency limit is a memory budget, not a QPS number" — that sentence is the senior signal of the whole question.

## Streaming — SSE, and why UX defines the SLO

Users can't wait 30s for a full answer, so tokens stream as generated — **SSE** (realtime lesson: one-way push = SSE, not WebSockets). The latency metrics change too: **TTFT** (time to first token — dominated by queue wait + prefill; the UX-critical one) and **inter-token latency** (steady decode rhythm). Say TTFT, not p99-of-total — total time mostly measures answer length.

## The classic exam followups

- **Multi-GPU:** model doesn't fit one GPU → **tensor parallelism** (split each layer across GPUs, chatty, within one node) and **pipeline parallelism** (split by layers, stage-to-stage, across nodes). One sentence each suffices.
- **Prefix caching:** many requests share long prefixes (system prompts, few-shot examples, chat history) — cache those KV blocks and reuse across requests. Huge TTFT win for chat products; connects to your prompt-caching knowledge from work.
- **Rate limiting is token-budget, not request-count** — one request can cost 100× another. Limit **tokens/minute per tenant** (the rate-limiter walkthrough's token bucket, literally refilling with LLM tokens), plus a max-concurrent-streams cap.
- **Model fleet:** requests routed by model; small-model fallback under load or for easy queries (gateway lesson, next-next). GPU autoscaling is slow (model load = minutes) → keep warm pools, scale on queue depth + TTFT, not CPU.
