## Why queues exist (the sentence version)

A queue turns "do this now, and if you're slow or dead the user suffers" into "write down that this must happen, and something will make it happen." You buy: **decoupling** (producer doesn't know consumers), **buffering** (absorb spikes, drain at your pace), and **retry-ability** (failures re-run instead of vanishing). You pay: **eventual, not immediate** (the work happens... soon), and a new component to operate.

This is your day-job territory (Kafka) — the goal here is making the interview version crisp.

## Queue vs log — the distinction interviewers test

<Mermaid code={`flowchart TD
    subgraph Q["Queue (SQS, RabbitMQ)"]
      M1["msg"] --> C1["consumer takes it,\nmessage is GONE"]
    end
    subgraph L["Log (Kafka, Kinesis)"]
      P1["append-only partitions"] --> C2["consumer group A\n(own offsets)"]
      P1 --> C3["consumer group B\n(own offsets)"]
    end`} />

| | **Queue** (SQS) | **Log** (Kafka) |
|--|----------------|-----------------|
| A message is… | consumed and deleted | appended and retained; consumers track their own **offset** |
| Consumers | compete for messages | each **consumer group** reads the full stream independently |
| Replay | no | yes — rewind the offset |
| Use | task distribution (send this email) | event distribution (order-placed → email svc, analytics, fraud all react) |

Rule of thumb: **one consumer type → queue; many independent reactions to the same events, or replay needed → log.**

## Ordering — precise or it's wrong

Kafka guarantees order **within a partition only**. Messages are routed to partitions by key (`hash(key) % partitions`). So:

- Need "all events for order 123 in order" → key by `order_id`. ✅
- Global total order across everything → one partition → no parallelism. Almost never the real requirement — say that.

Parallelism = number of partitions (each partition is consumed by at most one consumer in a group). Hot key (one entity producing most traffic) = hot partition — the same skew problem as sharding, same conversation.

## Delivery semantics — the "exactly-once" trap

An interviewer WILL poke this. The truth in three lines:

- **At-most-once**: fire and forget. Messages can be lost. Rarely acceptable.
- **At-least-once**: retry until acknowledged. Messages can be **duplicated**. This is the real-world default.
- **Exactly-once**: across arbitrary systems, effectively a myth. What exists is at-least-once delivery + **idempotent processing** — so duplicates are harmless.

The senior sentence: *"I'll take at-least-once and make the consumer idempotent — dedupe on message ID, or make the operation naturally idempotent (SET, not INCREMENT)."* How to build idempotency properly is the contention pattern lesson — here you just need the framing right.

Why duplicates are unavoidable: consumer processes the message, then crashes **before acknowledging**. The broker must assume failure and redeliver. There is no protocol fix — the ack and the side effect can't be made atomic across two systems without idempotency or transactions spanning both.

## The supporting cast (one line each, all deep-dive currency)

- **DLQ (dead-letter queue)** — after N failed retries, park the message aside instead of poisoning the queue forever; alert a human. *Every* async design should mention one.
- **Backpressure** — consumers falling behind: monitor **lag** (offset gap); autoscale consumers up to the partition count; beyond that, add partitions or shed load.
- **Retry with exponential backoff + jitter** — immediate retries against a struggling downstream make it worse; jitter prevents synchronized retry waves.
- **Visibility timeout** (SQS) — a taken-but-unacked message reappears after the timeout; too short = duplicates while still processing, too long = slow failure recovery.

## Where queues slot into designs

The recurring shape — write path returns fast, heavy work happens async:

You'll reuse this exact picture in: notifications, YouTube transcoding, web crawler, feed fan-out, job scheduler, ad aggregation. It's the async-pipelines pattern module later — this lesson is its vocabulary.
